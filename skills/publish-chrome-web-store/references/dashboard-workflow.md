# Chrome Web Store Dashboard 工作流程

只在需要操作 Dashboard 時載入本檔。Release asset 的下載與驗證交給 scripts，避免模型重複手算或從本機猜套件。

## 工具路由

1. 優先使用能沿用使用者 Chrome 登入狀態的 Chrome 控制工具。
2. 若頁面明確回報 `The extensions gallery cannot be scripted`，停止相同方法；截取最少必要證據。
3. 只有使用者已授權本機 UI 控制時，才改用 computer-use；否則先取得授權。
4. computer-use 每次動作後重新擷取 accessibility state。舊 element index 不得跨導頁、對話框或視窗切換使用。
5. 避免在截圖或輸出中暴露檔案選擇器內其他私人檔名；只擷取任務所需區域或文字。

## 上傳前檢查

- Dashboard publisher 帳戶正確。
- item ID 與專案 manifest／設定一致。
- 記下目前公開版本；它可能在新版本送審後仍維持不變。
- `VERIFIED_ASSET` 指向從 Release 下載並核對過的 extension ZIP。
- SHA-256、manifest version 與 tag 相符。
- 檔名或 Release 內容顯示為 Helper、Native Host、installer 時，不上傳。

若頁面落在開發者註冊、協議或付款頁，通常代表帳戶錯誤或尚未完成註冊。停止並請使用者處理，不代勾協議或付款。

## 套件上傳

1. 進入正確商品的「套件」頁。
2. 選「上傳新套件」，指定已驗證 ZIP。
3. 若 macOS 檔案選擇器在 `/tmp` 顯示檔案但「打開」停用：
   - 先用 `stage-upload-copy.sh` 複製到使用者指定且已存在的穩定目錄（通常是 Downloads）；
   - 在選擇器按 `Cmd+Shift+G`；
   - 輸入副本的完整路徑並按 Return；
   - 重新讀取 UI state，確認「打開」已啟用後再點擊。
4. 不優先嘗試 Finder 拖放；它受視窗排列與 drop target 影響，失敗率較高。
5. 等待上傳完成及頁面重新導向，不因短暫顯示 `0%` 就重複上傳。
6. 回到套件頁讀回草稿版本與目前公開版本，確認兩者各自正確。
7. 比較舊版與新版權限分類。新增權限、額外 host access 或不明警告時停止，先請使用者確認。

## 儲存與送審

依序檢查：

- 「狀態」：送審前顯示草稿未發布或取消發布，不代表上傳失敗。
- 「隱私權」：單一用途與每項權限理由完整。host access 可能延長審查，不一定是 blocker。
- 「發布範圍」：免費／付費、公開／不公開、地區皆符合既有設定與使用者要求。

然後：

1. 點「儲存草稿」。
2. 等待明確的成功訊息，例如「商品已儲存」，並確認「提交審查」可用。
3. 點「提交審查」，讀取最終確認對話框。
4. 依使用者意圖設定「通過審查後自動發布」。使用者要求「上架」且未指定分階段發布時通常勾選；只要求「送審」時不要自行擴大為自動發布。
5. 執行最終提交；這個動作必須已包含在使用者明確的發布授權中。
6. 等待「已提交審查」類成功訊息，關閉確認視窗後重新讀取頁面。
7. 只有讀回 `待審查` 或等價狀態，才宣告送審完成。

## 狀態語意

| 畫面狀態 | 可以宣稱 | 不可以宣稱 |
|---|---|---|
| 草稿版本已上傳 | 套件已上傳為草稿 | 已送審、已公開 |
| `待審查`／已提交 | 目標版本已送審 | 目標版本已公開 |
| 審查通過、等待發布 | 已通過審查 | 所有人都能安裝新版 |
| Dashboard `已發布 - 公開` | 某個版本目前公開 | 未核對版本前，不可說目標版本公開 |
| 匿名頁＋update service＋隔離安裝皆為目標版本 | 目標版本已公開 | — |

語系顯示 Approved、Dashboard 顯示「已發布」，仍可能只代表舊版。每次都同時回報「送審版本」與「目前公開版本」。

## 完成與收尾

- 保留審查頁供使用者查看。
- 關閉為上傳而開啟的 Finder 視窗，恢復 Chrome 原本視窗狀態。
- 不刪除 Release、tag 或 checksum。
- 上傳副本屬於新建立且可重建的檔案；是否刪除由使用者決定並在交付中明說。
- 使用交付範本記錄 Release 證據、Dashboard 證據與尚待公開驗收事項。
